# FoodMap 연구 진행 결과 - 2026-08-30

## 1. 오늘까지의 연구 목표

FoodMap의 목표는 자유로운 한국어 식사 기록에서 음식과 섭취 시점을
추출하고, 음식의 대표 구성요소를 확률적으로 표현한 뒤, 향후 웨어러블
건강 데이터와 연결해 개인별 FoodMap으로 발전시키는 것이다.

현재 연구는 건강 효과를 새로 증명하는 단계가 아니다. 먼저 텍스트를
재현 가능한 `MealEvent`와 음식-구성요소 관계로 바꾸고, 모호한 음식의
구성을 하나의 고정 레시피로 단정하지 않는 데이터 기반을 만드는 단계다.

## 2. 오늘 구현·확장한 내용

### 2.1 음식 사전 v0.3 확장

기존 v0.1 기준선은 보존하고, 별도 v0.3 확장 레이어를 추가했다. 이
방식은 기존 판단을 지우지 않고 새 행만 검토·수정할 수 있어 연구
재현성과 Git 기반 검토에 적합하다.

| 항목 | v0.1 기준선 | 현재 병합 수 | 변화 |
| --- | ---: | ---: | ---: |
| 표준 음식군 | 30 | 80 | +50 |
| 음식 별칭 | 65 | 142 | +77 |
| 구성요소 vocabulary | 68 | 94 | +26 |
| 음식-구성요소 주석 | 168 | 373 | +205 |
| 명시 구성요소 별칭 | 23 | 52 | +29 |

추가한 음식군에는 비빔밥, 된장찌개, 순두부찌개, 부대찌개, 제육볶음,
샤브샤브, 보쌈, 잡채, 카레, 오므라이스, 짜장면, 냉면, 현미밥, 두유,
오트밀, 통밀빵 등이 포함된다. `제육`, `샤브`, `돈가스` 같은 실제
입력 표현도 별칭으로 정규화한다.

### 2.2 대표 구성요소의 확률적 추론

음식명 하나가 항상 같은 재료를 뜻하지 않으므로, 각 음식-구성요소
연결에는 `core`, `typical`, `optional`, `variant` 역할과 Beta prior를
기록했다.

예를 들어 제육볶음은 돼지고기·고추장·매운맛을 높은 확률의 중심
성분으로, 마늘·대파·지방은 레시피에 따라 달라지는 후보로 둔다.
샤브샤브는 육수·잎채소·일반 단백질 재료를 대표 성분으로 두고,
버섯과 면 사리는 변동 성분으로 남긴다.

이 선택은 정확한 나트륨 g을 알 수 없는 일반 음식명에 가짜 정밀도를
부여하지 않기 위한 것이다. 현재 확률은 독립 레시피 빈도가 아니라
검토된 사전확률이며, 외부 관측값이 쌓일 때만 갱신된다.

### 2.3 텍스트 추출과 구성요소 처리 개선

- `비빔밥`을 인식하면서 내부의 `밥`을 별도 음식으로 잘못 추출하지 않게 했다.
- `두유`의 첫 글자 `두`를 수량 2로 잘못 읽지 않게 했다.
- `햄치즈 샌드위치`에서는 치즈를 독립 식사 음식으로 중복 기록하지 않고,
  샌드위치의 명시 구성요소로 처리한다.
- 반대로 `토마토랑 파스타`처럼 연결어가 있으면 토마토와 파스타를 두 음식으로 보존한다.

현재의 작은 학습 모델은 한국어 문자 n-gram 기반 다중 라벨 Naive Bayes다.
이는 학습 가능한 기계학습 기준선이지만 pretrained LLM은 아니다. 직접
사람이 작성한 샌드위치 예시 14개와 사전에서 파생된 약한 라벨 143개를
분리해 사용하며, 직접 라벨이 3개 미만인 음식에는 모델 확률을 출력하지
않고 사전확률만 사용한다.

음식 사전만 무작정 늘리기보다, 이 25개 음식의 레시피 변이를 먼저

총 목표는 1,050개 관측이다. 하나의 플랫폼에서 복제된 레시피를 여러 번

## 4. 외부 레시피 파일럿 수집

상위 5개 음식군에 대해 공개 레시피 기반 관측 10건을 정규화했다.

| 음식군 | 관측 수 | 상태 |
| --- | ---: | --- |
| 포케 | 2 | `pending_review` |
| 비빔밥 | 2 | `pending_review` |
| 햄버거 | 2 | `pending_review` |
| 카레 | 2 | `pending_review` |
| 보쌈 | 2 | `pending_review` |

각 행에는 음식 ID, 정규화 구성요소 ID, URL, 수집일, 출처 ID, 작성자
수준 독립성 그룹, 품질 가중치, 검토 상태가 있다. 레시피 원문과 이미지는
저장하지 않았다. 현재 파일럿은 하나의 사용자 작성 레시피 플랫폼에
기반하므로 보수적으로 가중치 0.35를 주었고, 아직 posterior 계산에
반영되지 않는다.

관측된 성분 중 현재 음식 후보에 없는 것은 자동 추가하지 않는다. 예를
들어 비빔밥에서 소고기·버섯·콩나물·마늘 등이 관측됐지만, 일반적인
비빔밥의 대표 성분으로 넣을지는 더 많은 독립 관측 뒤에 검토해야 한다.

## 5. 확률 갱신 방법

검토가 끝난 행만 posterior 계산기로 전달한다. 구성요소가 관측된 경우는
기존 `alpha`에 가중치를 더하고, 관측되지 않은 경우는 `beta`에 더한다.

```text
posterior_alpha = prior_alpha + 관측된 레시피 가중치 합
posterior_beta  = prior_beta  + 관측되지 않은 레시피 가중치 합
posterior_probability = posterior_alpha / (posterior_alpha + posterior_beta)
```

이 방식은 레시피가 한두 개뿐일 때 0% 또는 100%로 과도하게 확신하지
않도록 한다. 또한 후보 밖 성분은 `unmodeled_component_ids`로 보고해
사람이 확인한 뒤에만 사전 구조를 확장한다.

## 6. 데이터 구조 선택과 배운 점

### CSV: 사람이 검토하는 작은 기준 데이터

음식, 별칭, 구성요소, 주석은 아직 수백 행 규모라 CSV가 적합하다. 각
행의 수정 차이를 보기 쉽고, 식별자 오류를 검증하기 쉽다. 수집 큐도
검토자가 우선순위와 상태를 한눈에 보기 위해 CSV로 유지한다.

### JSONL: 출처가 있는 개별 레시피 관측

레시피 하나에는 여러 구성요소와 출처 메타데이터가 함께 들어가므로
JSONL을 선택했다. 한 행이 독립 관측 단위라 추가·삭제·검증이 쉽고,
원문 URL과 품질 가중치를 함께 보존할 수 있다.

### Parquet/DuckDB: 대규모 분석 단계

실제 식사 기록과 웨어러블 시계열이 많아지면 JSONL만으로 반복 조인이
비효율적이다. 그때는 이벤트·음식·관계 테이블을 Parquet으로 변환하고
DuckDB에서 시간대, 성분, 개인별 결과를 열 단위로 빠르게 집계한다.
현재처럼 기준 데이터를 자주 검토하는 단계에서는 CSV/JSONL이 더 단순하고
안전하다.

### 데이터마이닝 관점

현재의 핵심은 효과를 발견하는 것이 아니라 자유 문장을 음식, 시간,
구성요소, 불확실성이라는 분석 가능한 특징으로 변환하는 것이다. 이후
웨어러블 데이터가 들어오면 같은 사람의 식사 전후 시간 창을 연결해
연관성을 분석할 수 있다. 그때도 텍스트 추론의 확률과 출처를 함께
보존해야, 음식-건강 결과가 어떤 가정에서 나왔는지 검토할 수 있다.

## 8. 사용자가 검토할 항목

1. 파일럿 10행의 `food_id`, `component_ids`, URL, 독립성 그룹이 맞는지 확인한다.
2. 비빔밥·포케·햄버거·카레·보쌈에서 새로 관측된 성분을 일반 후보로
   추가할지, 더 많은 관측을 기다릴지 결정한다.
3. 승인한 행만 `review_status: approved`로 바꾼다. 승인 전에는 절대
   General FoodMap의 확률을 갱신하지 않는다.
4. 이후 공식 API 또는 다른 독립 제공자를 추가해 상위 5개 음식군부터
   목표 표본을 채운다.
