# FoodMap Daily Result - 2026-08-29

## 오늘의 목표

웨어러블 데이터와 연결하기 전에, 자유 문장 안에서 식사한 음식, 식사 시점, 양, 상태를 재현 가능하게 추출하고, 이후 음식 성분 및 개인 건강 반응과 연결할 수 있는 데이터 기반을 만든다.

## 오늘 구현한 결과

### 1. 텍스트를 MealEvent로 변환

- 한국어 식사 문장에서 `food_id`, 음식명, 섭취 시점, 식사 유형, 양, 단위, 수식어, 섭취 상태를 추출하는 MealEvent 파서를 구현했다.
- 추출 결과에 원문 위치(`source_span`)와 입력 행 ID를 남겨, 나중에 결과가 잘못되었을 때 원문으로 되돌아가 검토할 수 있게 했다.
- `비빔밥` 안의 `밥`처럼 사전에 없는 복합 음식에서 일부 음식명이 잘못 매칭되지 않도록 경계 검사를 추가했다.
- 초기 음식 사전에 없는 후보는 자동으로 확정하지 않고 `unresolved_food_candidates`에 보관한다. 이 목록은 사람이 확인한 뒤에만 음식 사전 확장에 사용한다.

### 2. 연관성 추출 파이프라인

- 한 문장 입력을 식사 이벤트, 이벤트-음식 연결, 관계, 미해결 후보, 출처 원장으로 분리해 출력하는 파이프라인을 만들었다.
- 관계는 `OCCURS_AT`, `CONTAINS_FOOD`, `HAS_QUANTITY`, `HAS_MODIFIER`, `HAS_COMPONENT` 형태로 저장한다.
- 이 구조로 "어떤 성분을 포함한 음식이 언제 먹혔는가"를 관계 조합으로 조회할 수 있다.
- 동일한 결과를 감사와 교환에 적합한 JSONL, 분석과 조인에 적합한 Parquet 두 형식으로 생성한다.
- DuckDB를 사용해 로컬에서 JSONL 결과를 Parquet로 변환하고, SQL 기반 탐색을 할 수 있게 했다.

### 3. 가상 인구 기반 기본 FoodMap과 개인화

- 실제 연구 참여자 데이터가 없는 현재 단계에서, 합성 프로필 30명과 14일 식사 기록을 생성했다.
- 기본 FoodMap에는 카페인-수면, 설탕/정제 탄수화물-식후 혈당, 나트륨-혈압의 세 가지 인구 수준 사전 관계를 포함했다.
- 각 관계에는 필요한 웨어러블 또는 센서 종류를 명시했다. 예를 들어 혈당 반응은 CGM, 혈압 반응은 혈압 측정기가 있어야 실제 관측으로 업데이트할 수 있다.
- 개인 FoodMap은 인구 사전값과 개인 관측값을 경험적 베이즈 방식으로 합친다. 관측이 적을 때는 일반적인 사전값에 가깝게 유지하고, 관측이 쌓일수록 개인 데이터의 비중을 높인다.

### 4. 출처와 재현성

- 음식 성분 연결, 입력 원문, 합성 데이터 생성, 논문 기반 사전 관계에 `source_ids`를 남겼다.
- `source_registry.json`에 출처 이름, URL, 해석 주의사항을 기록했다.
- 합성 실행 결과에는 시드와 생성 수치를 담은 실행 매니페스트를 남긴다. 같은 조건에서 결과를 다시 생성할 수 있다.

## 데이터베이스 관점에서 배운 점

### 식별자는 이름보다 중요하다

`아메리카노`, `아아`처럼 같은 음식을 여러 표현으로 입력하면 문자열만으로는 데이터가 분리된다. 따라서 모든 음식과 성분에 변하지 않는 `food_id`, `component_id`를 두고, 표현은 별칭 테이블에서 관리하는 방식이 안전하다. 데이터가 커질수록 이름을 수정하거나 언어를 추가해도 관계 데이터가 깨지지 않는다.

### 이벤트와 음식 연결을 분리해야 한다

한 끼에는 음식이 여러 개 들어갈 수 있다. 시간이나 사용자 같은 이벤트 공통 정보는 `meal_events`에 한 번만 저장하고, 음식별 양과 상태는 `meal_event_foods`에 저장했다. 이를 정규화라고 하며, 한 끼의 시간을 음식 수만큼 중복 저장하지 않아 수정 오류와 저장 낭비를 줄인다.

### JSONL과 Parquet은 역할이 다르다

JSONL은 한 행씩 읽고 쓰기 쉬우며 원문과 중간 결과를 감사하기 좋다. 반면 Parquet은 같은 열의 값을 묶어 저장하므로 "특정 성분, 특정 시간대, 특정 사용자"처럼 일부 열만 읽는 분석에 효율적이다. 따라서 JSONL을 추적 가능한 원본 결과로 유지하고, Parquet을 분석용 파생 형식으로 만들었다.

### 지금은 그래프 DB보다 관계 테이블이 적합하다

FoodMap은 음식-성분-건강지표가 연결된 그래프처럼 보인다. 그러나 초기 데이터 규모에서는 관계 테이블과 DuckDB SQL만으로도 필요한 조인과 집계가 충분하며, 검증과 수정이 단순하다. 관계가 수백만 건 이상으로 늘고 다단계 경로 탐색이 핵심 질의가 될 때 Neo4j 같은 그래프 DB를 검토하는 편이 합리적이다.

### 행 단위 출처가 연구 신뢰도를 만든다

"이 연결은 어디에서 왔는가"를 나중에 답할 수 있어야 연구 데이터가 된다. 그래서 입력 원문, 음식-성분 연결, 합성 생성 과정, 논문 기반 사전 관계에 출처 ID를 붙였다. 다만 현재 v0.1 음식-성분 연결은 내부 큐레이션 출처까지 추적되며, 168개 연결 각각에 대한 외부 근거는 아직 완성되지 않았다.

## 데이터마이닝 관점에서 배운 점

### 현재 단계는 효과 발견보다 정보 추출과 특징 구성이다

오늘 만든 것은 "설탕이 혈당을 올린다"는 새로운 인과관계를 발견하는 데이터마이닝이 아니다. 자유 텍스트를 분석 가능한 이벤트, 시간, 음식, 성분이라는 구조화된 특징으로 바꾸는 정보 추출과 특징 공학 단계다. 이 기반이 있어야 이후 웨어러블 시계열과 결합해 연관성 분석을 할 수 있다.

### 시간과 상태가 연관성의 핵심 변수다

음식명만 있으면 건강 반응과의 연결이 약하다. "어제 밤", "식후", "안 먹음", "반만" 같은 정보가 있어야 올바른 웨어러블 관측 구간을 잡고, 실제 섭취와 계획 또는 취소를 구분할 수 있다. 그래서 음식명보다 먼저 이벤트 시간과 섭취 상태를 보존했다.

### 사전 지식과 개인 데이터는 함께 써야 한다

개인 데이터가 적을 때 관측값 하나만 믿으면 우연한 변동에 흔들린다. 인구 수준의 문헌 기반 사전 관계를 출발점으로 두고, 개인 관측이 늘어날수록 조정하는 방식은 초기 개인화의 불안정성을 줄인다. 이는 개인화의 방향을 정하는 장치이지, 개인에게 이미 임상적으로 증명된 효과를 선언하는 방식은 아니다.

### 합성 데이터는 배관 검증용이다

합성 데이터는 입력부터 개인화 결과까지 흐름이 끊기지 않는지, 테이블 구조가 충분한지, 분석 코드가 동작하는지를 확인하는 데 유용하다. 그러나 합성 데이터에서 나온 연관성은 설계자가 넣은 가정을 다시 재현한 결과이므로 실제 사람에게 적용할 과학적 근거가 될 수 없다.

## 다음에 보완할 점

1. 식품의약품안전처 식품영양성분 데이터베이스와 실제로 연결해 음식-성분 값을 확장하고, 데이터 버전과 조회 날짜를 함께 기록한다.
2. 현재 36문장과 분리된 600문장 이상의 독립 코퍼스를 만들고, 음식·시간·양·상태를 라벨링해 일반화 성능을 평가한다.
3. 모든 음식-성분 연결에 외부 출처 또는 근거 수준을 추가한다. 불확실한 연결은 확정값 대신 검토 상태로 남긴다.
4. 실제 웨어러블 데이터가 들어오면 시간대 정렬, 결측값 처리, 활동·수면·약물 같은 교란 요인 기록을 먼저 설계한 뒤 연관성 분석을 시작한다.
